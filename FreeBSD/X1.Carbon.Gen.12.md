# Lenovo ThinkPad X1 Carbon Gen 12 on FreeBSD

Machine: ThinkPad X1 Carbon Gen 12 (21KDS08D00), Intel Core Ultra 7 165U (Meteor Lake-U).
Tested: FreeBSD 16.0-CURRENT main-n288456-240d81169286 (2026-08-21), GENERIC-NODEBUG.

## Device purpose

None of these devices blocks normal laptop use.
Firmware runs them, or they serve optional features.
The Linux driver name helps when porting or reading specs.

### Dynamic Tuning Technology (0:4:0)

Processor thermal device.
Firmware and the OS use it to manage CPU power limits (PL1/PL2) against skin temperature.
It exposes RAPL power limits over MMIO, power floor hints, and workload type hints.
Linux driver: `processor_thermal_device_pci` (int340x thermal).
Impact on FreeBSD: no OS-side power limit tuning; firmware/EC defaults apply.

### Gaussian & Neural-Network Accelerator (0:8:0)

Milliwatt-class coprocessor for always-on audio.
It scores small models on a microphone stream while the CPU stays in deep idle.
Details below come from memory, not checked against Intel documentation.

The name comes from classic speech recognition.
Before deep learning, recognizers scored audio against Gaussian Mixture Models (GMM).
The GNA speeds up GMM scoring and small neural networks (DNN, RNN/LSTM, small CNN).

Laptop uses:

- Wake word: listen for "Hey Cortana" or "Alexa" during idle or modern standby, without waking the CPU.
- Noise suppression: remove background noise from the microphone during calls.
  Some Intel and vendor audio stacks offloaded this job to the GNA.
- Small speech recognition: voice commands and keyword spotting. Real transcription is too big for it.

Compared with the NPU (0:11:0):
the GNA draws milliwatts and runs one audio stream at a time.
The NPU handles vision and bigger models at a few watts.
On Meteor Lake the two overlap, and the NPU can run the same audio models.

Status: dead end.

- Intel phases the GNA out in favor of the NPU; newer chips (Lunar Lake and later) drop it.
- OpenVINO had a GNA plugin, deprecated and then removed (around 2023-2024).
- Linux never merged a GNA driver; Intel's posted patches went nowhere.
- In practice, only Windows audio drivers and vendor software used it.

Impact on FreeBSD: none.
No driver exists anywhere to port, and the userspace stack is gone.

### Platform Monitoring Technology (0:10:0)

Intel "vendor-specific extended capability" device (VSEC).
It points to telemetry tables: power, thermal, residency counters, crash log.
Linux driver: `intel_vsec`, feeds `intel_pmt_telemetry` and `intel_pmt_crashlog`.
Impact on FreeBSD: no hardware telemetry; not needed to run.

### Neural Processing Unit (0:11:0)

Intel AI Boost NPU (VPU 3720).
Runs neural network inference offloaded by OpenVINO or Windows ML.
Needs firmware loaded by the OS driver.
Linux driver: `intel_vpu` (accel/ivpu).
Impact on FreeBSD: NPU unusable; CPU and iGPU still run inference.

#### NPU laptop use cases

An NPU saves power; it does not add speed.
It runs small, always-on inference jobs at a few watts, so the CPU and iGPU stay idle.
NPU 3720 gives about 11 TOPS INT8 (figure from memory, not checked): a small NPU.

Where the NPU helps on a laptop:

- Video calls: background blur, auto framing, eye-contact correction (Windows Studio Effects).
  On the CPU, these jobs drain the battery during long calls.
- Audio: noise suppression, voice isolation, wake word.
  The GNA (0:8:0) is the older, smaller block for the same jobs.
- Live captions and translation: local Whisper-class speech-to-text.
- Photo and file search: image tagging, semantic search, OCR in the background.
- Small local LLMs: possible with OpenVINO GenAI and 1-4B models.
  Decode stays slow because memory bandwidth limits it, as on the iGPU.
  On this chip the iGPU is often faster; the NPU wins only on watts.

Limits:

- Microsoft "Copilot+" features (Recall, Cocreator) need 40+ TOPS.
  Meteor Lake does not qualify; Lunar Lake and later do.
- Applications reach the NPU only through OpenVINO, ONNX Runtime, or DirectML, with models quantized for it.
  Arbitrary PyTorch or llama.cpp code does not run there.

To use the NPU on FreeBSD, three pieces are necessary:

1. A port of the Linux `intel_vpu` (ivpu) kernel driver, plus its firmware.
2. Intel's Level Zero NPU userspace driver.
3. OpenVINO.

That is a lot of work for little gain on this machine.
Occasional Whisper or blur jobs run well enough on the CPU or iGPU.
The only real gain is battery life during video calls, and no FreeBSD application would use the NPU for that.

### Thunderbolt DMA0/DMA1 (0:13:2, 0:13:3)

Native Host Interface (NHI) of the integrated Thunderbolt 4 / USB4 controller.
The OS uses NHI to manage the Thunderbolt fabric: device authorization, PCIe tunneling, USB4 routers.
USB 3 on USB-C ports uses the separate TCSS xHCI function, which attaches.
DisplayPort alt mode goes through i915.
Linux driver: `thunderbolt`.
FreeBSD has `thunderbolt(4)` code in `sys/dev/thunderbolt`, but it knows only Alpine Ridge, Ice Lake, and AMD Pink Sardine IDs.
Impact on FreeBSD: no PCIe tunneling, so Thunderbolt PCIe devices (eGPU, NVMe enclosure, dock NIC on PCIe) do not work.
Firmware may still set up a dock at boot.

### Shared SRAM (0:20:2)

Small on-chip SRAM shared by firmware engines: Power Management Controller (PMC), CSME and others.
Not RAM for the OS: the OS only maps the BAR and reads tables firmware stores there.
On Meteor Lake, the PMC is split into several units (SOC, IOE, PCH).
The SRAM holds discovery data for the extra units and PMT telemetry, including low-power residency counters.
Linux: read by `intel_pmc_core` (SSRAM telemetry code) for S0ix substate residency in debugfs.
Impact on FreeBSD: none at runtime; useful only for s2idle/S0ix debugging tools.
Pairs with PMT at 0:10:0.

### CSME HECI (0:22:0)

Host Embedded Controller Interface to the Converged Security and Management Engine (Intel ME).
The OS sends messages to ME firmware through it.
Users: firmware update, PTT (firmware TPM) management, AMT, content protection (HDCP, PAVP), platform status.
Linux driver: `mei_me`.
FreeBSD has no HECI message driver.
`hfsts(4)` lists this ID (8086:7e70), but it only reads ME firmware status registers from PCI config space and reports them via sysctl.
`hfsts` arrived in main 2026-09-15 (8e5e2c391059), after this kernel; it is a module, not in GENERIC.
Impact on FreeBSD: no ME firmware update from the OS; TPM works through `tpm(4)` (CRB), not HECI.

### SPI flash controller (0:31:5)

PCH controller for the SPI flash chip that stores UEFI firmware, ME firmware, and NVRAM variables.
The OS uses it only for flash reads/writes, for example `flashrom` or firmware dump.
Linux driver: `spi-intel-pci`.
FreeBSD `intelspi(4)` supports Meteor Lake LPSS general-purpose SPI controllers (7e27, 7e30, 7e46, ...), not this flash controller.
Impact on FreeBSD: no OS-side firmware flash access; use the vendor firmware update.

## Which drivers are worth the work

For daily laptop use, none of these drivers is worth much time.
Two existing settings give more battery life than any of these drivers, at no cost.

### Settings first

State measured on carbon, 2026-11-04:

```
dev.cpu.0.cx_supported: C1/1/1 C2/2/253 C3/3/1048
dev.cpu.0.cx_usage: 100.00% 0.00% 0.00% last 4665us
dev.cpu.0.cx_lowest: C1
hw.pci.do_power_nodriver: 0
```

- CPU C-states: the CPU never leaves C1 (sample taken on AC).
  `hw.acpi.cpu.cx_lowest` is a live sysctl: a change applies at once, no reboot.
  The `*_cx_lowest` rc.conf variables apply only through `/etc/rc.d/power_profile`.
  That script has `KEYWORD: nostart`: it does not run at boot.
  devd (`/etc/devd/power_profile.conf`) runs it only on an AC line change.
  Defaults: `economy_cx_lowest="Cmax"` (on battery), `performance_cx_lowest="NONE"` (on AC: leave the value unchanged).
  Result: after boot, the CPU stays in C1 until the charger is unplugged once.
  Plugging back in keeps Cmax, because NONE changes nothing.
  To get Cmax from boot, add `hw.acpi.cpu.cx_lowest=Cmax` to `/etc/sysctl.conf`.
  This is the biggest battery win in this document.
- Unattached devices: `hw.pci.do_power_nodriver=0` leaves the 9 driverless devices in D0.
  Levels in `pci_cfg_save()` (`sys/dev/pci/pci.c`) fall through, so level 1 is the most conservative:
  level 1 skips storage, display, memory (Shared SRAM), and base-peripheral (GNA) functions;
  level 2 skips display, memory, and base-peripheral; level 3 powers down every unattached function.
  Setting the sysctl at runtime does nothing by itself.
  The policy applies when a PCI driver loads (any `kldload` reprobes unattached functions) or on resume.
- Measure: compare the "Present rate" from `acpiconf -i 0` before and after each change.

### Drivers, ranked by value for effort

1. DTT processor thermal (0:4:0).
   Gives FreeBSD control of CPU power limits (PL1/PL2) through MMIO RAPL; FreeBSD has no RAPL control today.
   Use: tune for battery or for performance.
   Small, self-contained driver; Linux `processor_thermal_device_pci` is a clear reference.
   Best ratio.
2. PMC + PMT + Shared SRAM (0:10:0, 0:20:2).
   Reports S0ix residency: shows why the laptop does not reach deep idle.
   Helps FreeBSD suspend-to-idle (s2idle) work; no gain for daily use.
   Medium effort: parse PMT discovery tables, and Meteor Lake splits the PMC into several units.
3. Thunderbolt NHI (0:13:2, 0:13:3).
   `sys/dev/thunderbolt` already exists: first step is to add IDs 7ec2/7ec3 and see what breaks.
   Value depends on hardware: only Thunderbolt PCIe devices need it (eGPU, NVMe enclosure, PCIe-based dock).
   USB and DisplayPort on USB-C already work without it.
   Unknown: how far the FreeBSD driver gets with PCIe tunnel setup on integrated USB4.
   Testing needs a Thunderbolt device.

Skip:

- HECI (0:22:0): big protocol, little gain. `hfsts(4)` covers ME status; firmware updates go through UEFI capsules.
- SPI flash (0:31:5): only `flashrom` needs it; vendor updates handle the flash.
- NPU (0:11:0) and GNA (0:8:0): see their sections above.

### Test results (2026-11-04, runtime only, on AC power)

Cmax, set with `sysctl hw.acpi.cpu.cx_lowest=Cmax` (sysctl reports `C1 -> C8`).
CPUs 0-3 after 30 s idle:

```
C8 0.00% 1.89% 98.10%
C8 0.00% 0.90% 99.09%
C8 0.00% 0.00% 100.00%
C8 0.94% 6.60% 92.45%
```

D3 for unattached devices, set with `sysctl hw.pci.do_power_nodriver=N`,
then `kldload if_vte` (no matching hardware) to trigger a reprobe:

| Device | Level 0 | Level 1 | Level 3 |
|---|---|---|---|
| 0:4:0 DTT | D0 | D3 | D3 |
| 0:8:0 GNA | D0 | D0 | D3 |
| 0:10:0 PMT | D0 | D3 | D3 |
| 0:11:0 NPU | D0 | D3 | D3 |
| 0:13:2 TBT DMA0 | D0 | D3 | D3 |
| 0:13:3 TBT DMA1 | D0 | D3 | D3 |
| 0:20:2 Shared SRAM | D0 | D0 | D3 |
| 0:22:0 HECI | D0 | D3 | D3 |

0:31:5 (SPI flash) has no PCI power management capability, so it stays in D0.
At level 3: no new kernel messages, Wi-Fi stays associated, ping to the gateway works.

### Battery discharge (2026-11-04, on battery, idle)

Method: switch config at runtime, wait 60 s, then read "Present rate" from `acpiconf -i 0` 18 times, 10 s apart.

| Config | Average draw |
|---|---|
| Baseline: cx_lowest C1, unattached devices D0 | 9064 mW |
| Cmax, unattached devices D0 | 6755 mW |
| Cmax, unattached devices D3 (level 3) | 6752 mW |

- Cmax saves about 2.3 W at idle: 25% less draw, about 1.34x battery life.
  The C1 baseline is the state after boot, before any AC line change.
  The default devd rule would have set Cmax at unplug; the test script set each value explicitly.
- D3 for unattached devices gives no measurable gain (3 mW, below noise).
- The EC smooths "Present rate": samples drift slowly after each change, so small differences are not reliable.

Conclusion: set Cmax permanently with `hw.acpi.cpu.cx_lowest=Cmax` in `/etc/sysctl.conf`. Leave `hw.pci.do_power_nodriver` at 0: no measured gain, and suspend/resume with level 3 is not tested.

Not tested yet:

- Suspend/resume with level 3 active.

Persistence: after reboot on battery, with no AC line change, `hw.acpi.cpu.cx_lowest` reads C8 from `/etc/sysctl.conf`.
CPUs 0-3 spend 80-94% in the deepest state; draw settles at 6741 mW about 2 minutes after boot.

## Touchpad interrupt and polling cost

`dmesg` shows, on every boot:

```
iichid0: <ELAN06D4:00 04F3:32B5 I2C HID device> at addr 0x15 on iicbus0
iichid0: Interrupt setup failed
iichid0: Using sampling mode
```

Cause: with the BIOS variable `TPDM == 0`, the touchpad `_CRS` (`\_SB_.PC00.I2C0.TPD0`) returns a GpioInt on the Meteor Lake GPIO controller (`\_SB_.GPI0`, INTC1083).
FreeBSD cannot deliver that interrupt on amd64:
there is no Meteor Lake GPIO driver, `acpi_iicbus.c` ignores GpioInt resources ("Not supported by FreeBSD yet"),
and `gpio_alloc_intr_resource()` returns NULL without INTRNG.
iichid then polls the touchpad: 10 Hz when idle (`dev.iichid.0.sampling_rate_slow`),
80 Hz after activity (`sampling_rate_fast`), back to 10 Hz after 16 empty polls (`sampling_hysteresis`).

### Polling cost (2026-11-05, on battery, idle, touchpad not touched)

Method: same as above (60 s settle, 18 samples of "Present rate" 10 s apart).
Polling stopped with `devctl detach iichid0`.

| Window | Touchpad state | Average draw |
|---|---|---|
| 1 | iichid attached, polling at 10 Hz | 6793 mW |
| 2 | iichid detached, no polling | 6708 mW |
| 3 | still detached (re-attach failed) | 6697 mW |

- Re-attach failed: after `devctl detach`, the device loses its name, so `devctl attach iichid0` returns ENOENT.
  `kldunload iichid; kldload iichid` restores the touchpad.
  Window 3 therefore repeats the detached state; the planned attached/detached/attached order did not happen.
- Window 1 samples drift down steadily (6861 to 6756 mW): the EC was still settling from earlier activity, which inflates the window 1 average.
- Result: idle polling costs at most about 90 mW (about 1.3% of idle draw), probably less.
  This is an upper bound, not a measurement of the cost; a clean attached/detached/attached run is still needed.

Value of real interrupts for this touchpad: lower latency on the first touch after idle
(up to 100 ms at 10 Hz polling) and no dropped reports during fast movement, more than battery life.
