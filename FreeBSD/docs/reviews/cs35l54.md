# Bugs

Both first-review bugs are fixed, in the commit that introduced each:

- **efirt (was POSTCR-c02d906e3e3f-1).** 7da96d9abad7 adds `efi_var_get()`
  and `MODULE_DEPEND(cs35l54, efirt, 1, 1, 1)` together. efirt.c declares
  `MODULE_VERSION(efirt, 1)`, and efirt.ko is built on amd64
  (sys/modules/Makefile `_efirt`), so the dependency resolves for both
  `options EFIRT` kernels and the module. 624257ddc91a, the first commit
  that hooks the module into the build, adds it under
  `MACHINE_CPUARCH == "amd64"` only; `cmi` keeps its i386/amd64 block.
  Unconditional `MODULE_DEPEND` (no `ARCH_MAY_USE_EFI`) is correct for an
  amd64-only module. Before 624257ddc91a the module is not reached from
  sys/modules, so no intermediate commit builds it on i386.
- **cs_play partial failure (was POSTCR-ae547a2c03ce-1).** In 44f7bb5a7c24,
  both error exits of `cs_play()` now `goto fail`, which calls `cs_stop()`
  on every amplifier and returns the error; `cs_set_playing()` leaves
  `playing` false, which now matches the hardware. `cs_stop()` on
  amplifiers never started is harmless: it wakes each one, its per-amp
  errors are ignored, and it continues to the next amplifier. The
  forward prototype `static int cs_stop(...)` precedes `cs_play()` in
  every commit (checked at each of the 9 revisions).

- **Still open from the first review, unchanged, none a bug:**
  - The firmware download (seconds) and the resume reload run on the shared
    `taskqueue_thread`. A private taskqueue would avoid stalling other users.
  - Mountroot window: `root_mounted()` is checked before the `mountroot`
    handler is registered (attach, around line 1161). Register first, then
    check.
  - `cs_apply_cal()` index fallback does not require `time[0] || time[1]`;
    an all-zero entry writes CAL_R 0 instead of playing uncalibrated.
  - `cs35l54_suspend()` blocks on `sc->lock` for the rest of a running
    download.
  - `cs_get_amps()` trusts `_DSD` (no UUID check, no 7-bit address check).
  - `cs_find_ctl()` pointer-compare overflow is moot now that the module is
    amd64-only.
  - ig4 stale-first-word workaround: comment and BUGS entry kept.
  - Headphones: the tutorial still does not say whether the amplifiers keep
    playing when hdaa automutes the speaker.
- **hdaa event, locking, I2C, dependencies.** These are unchanged since
  the first review, and its analysis still applies: no regression for
  other hdaa users, no LOR, a correct detach order, and safe failure
  without amdgpio, the ig4 clock fix or the firmware port.
- **Hardware.** On the ZBook, the old and the reworked modules both play a
  3 s tone as about 1 s. That is the amplifier start-up latency (the stream
  start is lost while the amplifiers start), not a regression from the
  rework. Worth a BUGS line in the man page, since users will notice it.

## Analysis

- **Task serialization.** fw_task, play_task, resume_task (which calls
  `cs_fw_task()` inline) and idle_task all run on the single
  `taskqueue_thread`, so they never run concurrently; only sysctl,
  suspend and detach run elsewhere, and all take `sc->lock`.
  `sc->stream` is written unlocked by the event handler, but every
  consumer reads it under the lock and every change enqueues play_task,
  which runs after any idle_task already queued. Stream on/off flapping
  ends in the right state: on cancels the timer and either keeps playing
  (pause window) or skips the setup (ready window); off while playing
  rearms the 1 s pause. `taskqueue_enqueue_timeout()` from inside
  `cs_idle_task()` is the usual self-rearm.
- **Detach.** The hdaa event is deregistered first, so no new play_task.
  play_task and fw_task, the only other arming paths, are drained before
  `taskqueue_drain_timeout()`, which also blocks the self-rearm
  (DT_DRAIN_IN_PROGRESS). A task that passed its `detaching` check before
  the unlocked store can still arm the timer, but that happens before its
  own drain returns. Then `cs_stop()` on `playing || ready` releases
  amplifiers left in the ready window. Correct.
- **Suspend.** It takes the lock, sets `suspended`, cancels the timer (a
  task already blocked on the lock sees `suspended` and returns) and
  `cs_stop()` clears `ready` unconditionally, even when I2C fails. A
  download in progress finishes first (suspend waits on the lock), then
  its ready timer is cancelled and the amplifiers stopped.
- **Resume / reload.** `ready` is false on every resume, because suspend
  cleared it, so a resume without reload does the full wake and setup
  (the `cs_resume_task()` comment stays true), and the reload path enters
  `cs_fw_task()` with `ready` false; that sets it again only after all
  amplifiers loaded. The reload branch clears `loaded` and `playing` but
  not `ready`; harmless today since suspend already cleared it, but
  `sc->ready = false` there would make it independent of suspend. Nit.
- **Setup skipped after a download.** `cs_load_amp()` ends with
  PREVENT_HIB + setup table, calibration, then AUDIO_REINIT. Linux
  cs35l56_hda_fw_load() has the same order (PREVENT_AUTO_HIBERNATE,
  regcache_sync, calibration, AUDIO_REINIT) and `cs35l56_hda_play()`
  then only sends AUDIO_PLAY, without rewriting registers, while the
  device stays runtime active. So playing within 3 s of a download
  without `cs_setup()` matches Linux. Not covered by the hardware test
  (the first tone was a cold start); one play right after `kldload` would
  confirm it on this laptop.
- **Amplifier hibernates while `ready`.** Not expected with PREVENT_HIB
  in effect. If it happened, the first `CS_USER_VOLUME` write NAKs,
  `cs_play()` fails, `cs_stop()` clears `ready`, and that stream stays
  silent; the next stream start does the full wake. Self-healing, no
  hang. Optional: retry once with the full wake when the setup was
  skipped.
- **Sysctls.** `volume` is written only while playing; `cs_play()` writes
  it at every start, so a change in the ready window applies to the next
  stream. `play`=0 clears both flags; a pending timer then finds nothing
  to do. `play`=1 while a pause or ready timer is pending is undone by the
  timer within 1 to 3 s (the timer pauses whatever plays). Test knob only,
  not a bug; worth a word in the man page ("Writing 1 ... starts them
  until the next stream stop or idle timeout") or arm nothing there.
  `play` also reads 1 for one second after the stream stops.
- **Power after boot.** Before this commit a download with no stream left
  every amplifier in PREVENT_HIB until the first stream stopped; now the
  ready timer releases them 3 s after the download. Good, and not in the
  commit message. A failed download still leaves the amplifiers already
  loaded with hibernation prevented (pre-existing, 4bdab8aea22a and
  earlier; power only).
- **cs_play().** Waking all four (3.2 ms each), then waiting for boot and
  setting up, then volume + PLAY on all, then the PS0 poll and the ASP
  enable per amplifier, is the same register sequence per amplifier as
  before, reordered across amplifiers. The error path still stops all.
  `cs_stop()` from the idle timer wakes amplifiers that are awake; costs
  13 ms, harmless.
- **Man page.** Dropping the "about two seconds to start" BUGS line is
  right: the tutorial records that the 1 s tones came from the test
  (`cat > /dev/dsp4` closing the device after 149 ms), and the new
  measurement shows a cold start at 50 ms with 2.90 s of a 3 s tone heard.
  Nothing else changed in the page (diff against fe07324d81f3: -3 lines).
