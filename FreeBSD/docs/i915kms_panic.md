# Debugging an `i915kms` kernel panic on FreeBSD

A walkthrough of a real kernel crash that happened on `CarbonX1`
(Lenovo ThinkPad X1 Carbon, Intel **Meteor Lake-P** iGPU, PCI ID
`8086:7d45`) while loading the Intel graphics driver `i915kms.ko` on
**FreeBSD 16.0-CURRENT**.

The goal here is pedagogic: we explain *every* step of how a kernel
core dump is analysed on FreeBSD, what each `kgdb` command does, and
how we read the resulting backtrace to find the root cause.

If you are new to kernel debugging, read this top to bottom. If you
already know `kgdb`, jump to [Root cause](#root-cause).

---

## 1. What we know before opening the dump

- **Machine:** `CarbonX1`, amd64, FreeBSD 16.0-CURRENT
  (`#1 n286843-75aadc902298`, built `2026-06-22`).
- **Symptom:** the box panics shortly after `kldload i915kms`.
- **Symptom seen on the console:** `panic: page fault`.
- **What the user changed recently:** `/boot/loader.conf` was edited
  to set `hw.i915kms.enable_guc=2`. This was **not a random tweak**
  — earlier boots with `enable_guc=0` (or unset) showed repeated
  `GT0: GUC: TLB invalidation response timed out for seqno 1` errors
  in dmesg, and the user changed the value to `2` (HuC-only, GuC
  submission off) as an attempted workaround. The kernel then
  panicked the next time `i915kms` was loaded.
- **Resolution (spoiler):** `hw.i915kms.enable_guc=3` (full GuC+HuC,
  the upstream Linux default for MTL) avoids the panic entirely. The
  reasoning behind that choice is in §5.1; if you only want the fix,
  jump there.
- **Where the dump landed:** `/var/crash/` on the laptop.

That is the bug report we start with. Everything else we are going to
*prove* from the dump.

### 1.1. The kernel we are debugging

```
FreeBSD 16.0-CURRENT #1 n286843-75aadc902298:
    Mon Jun 22 13:30:27 CEST 2026
    root@bigone:/usr/obj/usr/src/amd64.amd64/sys/GENERIC-NODEBUG
```

`GENERIC-NODEBUG` is a stock kernel **with full DWARF debug symbols**
(they end up in `/usr/lib/debug/boot/kernel/kernel.debug`) but with the
*runtime* kernel-debug features turned off:

| Option       | What it does                                       | In `GENERIC-NODEBUG`? |
|--------------|----------------------------------------------------|-----------------------|
| `INVARIANTS` | Cheap runtime assertions sprinkled across the code | No                    |
| `WITNESS`    | Lock-order tracking, dynamic deadlock detector     | No                    |
| `MALLOC_DEBUG_MAXZONES`, `DEBUG_VFS_LOCKS`, etc. | More expensive sanity checks | No |
| **Symbols (`-g`)** | Names + line numbers in `kgdb`               | **Yes**               |

In other words: we *can* still ask `kgdb` "what line of C is this
instruction in?", but we get **no help** from WITNESS telling us
"lock X was held while you tried to take lock Y" and no INVARIANTS
assertion firing earlier with a more informative message. The crash is
the first complaint we get.

### 1.2. Files left behind by `savecore(8)`

After the kernel panics, the bootloader brings us back to userland,
`/etc/rc.d/savecore` runs and copies the dump out of the dump device
into `/var/crash/`:

```
$ ls -lat /var/crash/
core.txt.0       <- textual summary, generated by crashinfo(8)
core.txt.last    -> core.txt.0
vmcore.0         <- 1.1 GiB raw kernel memory image
vmcore.last      -> vmcore.0
info.0           <- header: arch, kernel version, panic string
info.last        -> info.0
```

Quick sanity check on `info.0`:

```
Architecture: amd64
Dumptime:    2026-06-28 18:28:06 +0200
Panic String: page fault
Dump Status: good
```

`Dump Status: good` is important: it tells us `savecore` was able to
read the whole image off the dump partition without truncation.

### 1.3. `core.txt.0` vs `vmcore.0`

`crashinfo(8)` runs `kgdb` on the dump and saves the output as a text
file (`core.txt.0`). It includes the panic string, a `bt` (backtrace)
for the panicking thread, `ps`, `vmstat`, `netstat`, dmesg, etc.

Read `core.txt.0` first. It is almost always enough to know what
happened. Open `vmcore.0` in `kgdb` only when `core.txt` is missing
information you need (a register, a structure dump, a particular
thread, ...).

## 2. Reading the panicking thread's backtrace

The first useful block in `core.txt.0` is the panicking thread's call
stack. Here are the frames that matter (lower number = deeper in the
call chain at the moment of the crash; frame 0 is the top of the
stack, `panic()` is just below the trap handler):

```
#13 trap_pfault         (frame=0xfffffe00fd01a660, usermode=false, ...)
#14 <signal handler called>           <-- the page fault took us here
#15 linux_wake_up       (wqh=0xfffffe00fd01a6e8, state=3, nr=1, locked=false)
        at /usr/src/sys/compat/linuxkpi/common/src/linux_schedule.c:280
#16 wake_up_all_tlb_invalidate ()        from /boot/modules/i915kms.ko
#17 intel_uc_suspend ()                  from /boot/modules/i915kms.ko
#18 intel_gt_suspend_late ()             from /boot/modules/i915kms.ko
#19 intel_gt_init ()                     from /boot/modules/i915kms.ko
#20 i915_gem_init ()                     from /boot/modules/i915kms.ko
#21 i915_driver_probe ()                 from /boot/modules/i915kms.ko
#22 linux_pci_attach_device (...)
        at /usr/src/sys/compat/linuxkpi/common/src/linux_pci.c:644
#23 DEVICE_ATTACH ...
#24 device_attach ...
#25 device_probe_and_attach ...
#26 bus_generic_driver_added ...
...
#31 i915kms_evh ()                       from /boot/modules/i915kms.ko
#32 module_register_init (arg=<i915kms_md>)
#33 linker_file_sysinit  (lf=0xfffff8000334f180)
#34 linker_load_file     (filename="/boot/modules/i915kms.ko", ...)
#35 linker_load_module   (modname="i915kms", ...)
#36 kern_kldload         (td=..., file="i915kms", ...)
#37 sys_kldload          (...)
#38 syscallenter ...
#39 amd64_syscall        (td=...)
#40 <signal handler called>
```

How to read this:

- Frame `#37 sys_kldload` proves the crash happened inside the
  `kldload(2)` syscall — i.e. **while we were loading a module**.
- Frame `#34` confirms the module being loaded is
  `/boot/modules/i915kms.ko`.
- Frames `#22 → #21` show LinuxKPI handing control to the i915
  driver's `probe()` routine, `i915_driver_probe`. That is the
  per-device initialisation entry point.
- Frames `#21 → #20 → #19` are the normal init path of i915:
  `probe → gem_init → gt_init`.
- Frame `#18` is the bombshell. **`intel_gt_suspend_late` is i915's
  shutdown helper.** It has no business running inside `intel_gt_init`.
  The only way the call stack can look like this is if `intel_gt_init`
  is on its **error-rollback path**: init failed, so the driver is
  trying to undo what it just did.
- Frame `#15` is where the page fault actually occurred:
  `linux_wake_up`, line **280** of
  `/usr/src/sys/compat/linuxkpi/common/src/linux_schedule.c`.

So the one-sentence summary, without yet running a single `kgdb`
command ourselves, is:

> i915 failed to initialise the GT (graphics tile), entered its
> rollback code, and the rollback dereferenced something that was
> never set up.

Everything below is just confirming this and pinpointing the
"something".

## 3. Looking at the line that faulted

Two hosts are in play, and the source trees split across them:

| Host     | Role                          | What lives there                                              |
|----------|-------------------------------|---------------------------------------------------------------|
| `carbon` | crashed laptop (MTL iGPU)     | `/usr/src/sys/` — FreeBSD kernel + LinuxKPI source            |
| `bigone` | dev / package builder         | `/usr/ports/graphics/drm-latest-kmod/` — i915 / DRM port; also built the kernel running on `carbon` (see the `Version String`: `root@bigone:/usr/obj/usr/src/...`) |

`carbon`'s `/usr/ports` is empty — the port tree was never checked
out there, and the running `i915kms.ko` was installed as a binary
package built on `bigone`. Read the i915 / DRM source on `bigone`;
read the kernel and LinuxKPI source on `carbon` (or on `bigone`,
since the kernel was built there from the same `/usr/src`).

A look inside the built module confirms where the binary was
compiled:

```
$ strings /boot/modules/i915kms.ko | grep -m1 drm-kmod
/wrkdirs/usr/ports/graphics/drm-latest-kmod/work/drm-kmod-drm_v6.12/...
```

`/wrkdirs/...` is the `WRKDIRPREFIX` used by the ports build on
`bigone`. On `bigone` the source becomes readable at
`/usr/ports/graphics/drm-latest-kmod/work/drm-kmod-drm_v6.12/`
after `make extract`.

Frame `#15` points at `linux_schedule.c:280`. Here is the function in
the in-tree LinuxKPI:

```c
// /usr/src/sys/compat/linuxkpi/common/src/linux_schedule.c

273  void
274  linux_wake_up(wait_queue_head_t *wqh, unsigned int state, int nr, bool locked)
275  {
276      wait_queue_t *pos, *next;
277
278      if (!locked)
279          spin_lock(&wqh->lock);
280      list_for_each_entry_safe(pos, next, &wqh->task_list, task_list) {
281          if (pos->func == NULL) {
                  ...
288          }
289      }
290      if (!locked)
291          spin_unlock(&wqh->lock);
292  }
```

Line 280 walks the linked list `wqh->task_list`. To do that it has to
**dereference `wqh`** repeatedly: read `wqh->task_list.next`, then
`->next->next`, etc.

What the CPU actually faulted on tells us *how far* the list walk
got. From the trap frame (frame 13):

```
tf_addr   = 1                          # %cr2 = the faulting address
tf_rbx    = 1                          # %rbx held the bad pointer
tf_rip    = 0xffffffff80eab335         # = linux_wake_up+181
```

And the instruction at that address:

```
(kgdb) x/i 0xffffffff80eab335
   0xffffffff80eab335 <linux_wake_up+181>:   mov    (%rbx),%rbx
```

`mov (%rbx),%rbx` with `%rbx = 1` is "dereference virtual address
`1`, store the result back into `%rbx`". In source terms it is the
`pos = pos->next` step of `list_for_each_entry_safe` — the **list
walk is already one iteration in** and got fed a pointer of `1`. So
whatever was at `wqh->task_list.next` for this call was a valid-ish
pointer (the first iteration didn't fault) but the *next* hop landed
on `0x1`.

### 3.4. The honest limit of what this dump can tell us

At this point one is tempted to print `*wqh` and read off the
garbage. `kgdb` is happy to oblige:

```
(kgdb) frame 15
(kgdb) print wqh
$2 = (wait_queue_head_t *) 0xfffffe00fd01a6e8
(kgdb) print *wqh
$3 = {lock = {lock_object = {
        lo_name   = 0x3b003b00000001 <Cannot access memory ...>,
        lo_witness = 0xffffffff80eab335 <linux_wake_up+181>},
      mtx_lock = 32},
      task_list = { next = 0x10217,
                    prev = 0xfffffe00fd01a720 }}
```

Tempting story: "the structure is garbage, so the wait queue was
never initialised". **Don't fall for it.** Two reasons:

**(a) The `wqh` value kgdb shows is suspect.** `linux_schedule.c` is
compiled with `-O2`; the locals in the listing are
`pos = <optimized out>, next = <optimized out>`. DWARF tracks where
*each* variable lives per-PC, and for arguments like `wqh` the
compiler is free to keep the value in a register for a while, spill
it to a stack slot, reuse the register for something else, etc. When
we ask "where does `wqh` live at PC=linux_wake_up+181?", DWARF gives
us **one** location. If that location is a stack slot whose contents
have since been overwritten (very common at `-O2`), `print wqh`
prints whatever is there now — not what was passed in. Compare:

```
(kgdb) print &wqh
$4 = (wait_queue_head_t **) 0xfffffe00fd01a728      # DWARF location
(kgdb) x/gx 0xfffffe00fd01a728
0xfffffe00fd01a728:   0x0000000000000028           # value: 40 decimal
```

The byte pattern at the stack slot kgdb identifies as "wqh" is
`0x28` — not a pointer at all. So the `0xfffffe00fd01a6e8` kgdb
showed for `wqh` came from some *other* DWARF rule (a register that
also held `wqh` at this PC), and the `*wqh` dereference printed
bytes from a stack region that may or may not be related to the
real wait queue.

**(b) The source disagrees with the easy theory.** Reading the i915
driver source on `bigone` —
`drivers/gpu/drm/i915/gt/uc/intel_guc_submission.c` lines 1859..1871
— shows that `wake_up_all_tlb_invalidate()` does **not** declare a
`wait_queue_head_t` on its stack. It iterates `guc->tlb_lookup`
(an `xarray`) of heap-allocated `struct intel_guc_tlb_wait`, each
of which has its `wq` initialised by `init_tlb_lookup()` with
`init_waitqueue_head(&wait->wq)` (line 2059). So the wait queue
that `linux_wake_up` was called on **is** properly initialised at
allocation time — IF the xarray entry it came from is still live.

What this dump can confidently support:

1. The CPU was running `linux_wake_up`, the list walk got *one*
   hop in, and the second hop pointed at address `0x1`.
2. The caller is `wake_up_all_tlb_invalidate` (the only thing in
   `i915kms.ko` that calls into `linux_wake_up` along this
   path-suffix; symbol resolved by name).
3. That caller does
   `xa_for_each(&guc->tlb_lookup, i, wait) wake_up(&wait->wq);`
   — so what we were walking is one of `wait->wq.task_list`.
4. We **cannot** distinguish from this dump alone between
   (i) the `wait` object was freed under us (use-after-free) and
   the xarray still pointed at the freed memory,
   (ii) the `wait->wq.task_list` was corrupted by a concurrent
   writer (e.g. another reset path running in parallel),
   (iii) memory ordering between `xa_alloc` and the dereference
   gave us a torn pointer.

Distinguishing those needs a debug-built `i915kms.ko` so frames
`#16 .. #21` resolve to file:line, plus ideally LinuxKPI built at
`-O0` (or `-Og`) so `wqh` isn't optimised out. See §7 for the
rebuild recipe.

### 3.5. Why this code path was hit so much: the GPU was hanging in a loop

The kernel message buffer captured in the dump (extracted with
`kgdb` — see §4.x) is full of, in order:

```
drmn0: [drm] GPU HANG: ecode 12:1:5669c05a
drmn0: [drm] Resetting ccs'0 for CS error
drmn0: [drm] GPU HANG: ecode 12:1:1b9bc5f4
drmn0: [drm] Resetting bcs'0 for CS error
drmn0: [drm] GPU HANG: ecode 12:1:1bbb78b7
drmn0: [drm] Resetting rcs'0 for CS error
drmn0: [drm] GT0: Resetting chip for stopped heartbeat on ccs'0
drmn0: [drm] GT0: GuC firmware i915/mtl_guc_70.bin version 70.53.0
drmn0: [drm] GT0: GUC: submission disabled
drmn0: [drm] GT0: GUC: SLPC disabled
...  (the pattern repeats many times)
```

`rcs'0`, `bcs'0`, `ccs'0` are the **render, blitter and compute
engines** of the Meteor Lake GT. `GPU HANG: ecode …` is i915
declaring a per-engine hang detected by its heartbeat watchdog. The
follow-up `Resetting <engine>` is i915 trying to recover that one
engine; once enough resets pile up, it escalates to
`Resetting chip` — a full GT reset that re-loads GuC firmware (the
`GuC firmware i915/mtl_guc_70.bin version 70.53.0` line you see
after the "Resetting chip" line). The chain repeats.

How long was the machine up when it panicked?

```
(kgdb) print time_uptime
$4 = 76
```

Seventy-six seconds. All those hundreds of hangs and resets happened
in the **single** `kldload i915kms` syscall — the syscall on the
bottom of the panic backtrace is still in flight; it never returned.
`i915_driver_probe()` was submitting initial workloads to the GPU as
part of probe (display init, GuC self-tests, etc.), each one was
hanging, and i915 was running its reset machinery in a tight loop
from inside probe.

One of those resets called `wake_up_all_tlb_invalidate()`. That
function walks `guc->tlb_lookup` (an xarray of heap-allocated
`intel_guc_tlb_wait` objects) and calls `wake_up(&wait->wq)` on
each. One of those `wait->wq.task_list` lists held a pointer of
`0x1` after one hop — see §3.4 for what we can and cannot conclude
about *why*.

## 4. Reproducing the analysis with `kgdb` (the pedagogic part)

`core.txt.0` was generated by `crashinfo(8)`, which is just a wrapper
around `kgdb(1)`. Let us redo the analysis by hand so you understand
what the tool does for you.

### 4.1. Starting `kgdb` on a dump

```
# kgdb /boot/kernel/kernel /var/crash/vmcore.0
```

- First argument: the **kernel image** that was running. `kgdb`
  follows symlinks and also reads
  `/usr/lib/debug/boot/kernel/kernel.debug` for DWARF info.
- Second argument: the **vmcore** to inspect. Equivalent to
  pointing gdb at a userland core file.

`kgdb` (which is just `gdb` with extra commands and a kernel-aware
target) automatically loads every `.ko` whose address range appears
in the dump. You should see lines like:

```
Reading symbols from /boot/kernel/kernel...
Reading symbols from /usr/lib/debug//boot/kernel/kernel.debug...
Reading symbols from /boot/modules/i915kms.ko...
(No debugging symbols found in /boot/modules/i915kms.ko)   <-- !
Reading symbols from /boot/modules/drm.ko...
(No debugging symbols found in /boot/modules/drm.ko)       <-- !
```

The `(No debugging symbols ...)` line is important. **`i915kms.ko`,
`drm.ko`, `ttm.ko` and `dmabuf.ko` are out-of-tree.** They come from
the `graphics/drm-latest-kmod` port and are not built with `-g` and
not shipped with `.debug` companions. That is why our backtrace has
plain function names but no file/line info for any frame inside
`i915kms.ko`. The in-tree pieces (kernel itself, `linuxkpi`,
`linker`, `kld`) *do* have full source-level resolution.

> Aside: you can fix this for future debugging by rebuilding the
> port with `make WITH_DEBUG=yes` from
> `/usr/ports/graphics/drm-latest-kmod/` on `bigone` (where the
> port tree lives and where the current package was built), then
> installing the resulting package on `carbon`. The build produces
> `.debug` files under `/usr/lib/debug/boot/modules/`. Out of scope
> here.

### 4.2. The first three commands every kernel debugger uses

Once `kgdb` is at its `(kgdb)` prompt:

```
(kgdb) bt
```

`bt` (backtrace) is `kgdb`'s shorthand for "print the call stack of
the *current* thread". On a vmcore the "current thread" is the one
that called `panic()` — i.e. the panicking thread. This is what
produces frames `#0..#41` we showed in section 2.

```
(kgdb) frame 15
```

`frame N` selects frame `N` so subsequent commands operate on it
(register values, local variables, source line). Frame 15 is
`linux_wake_up`.

```
(kgdb) list
```

After selecting a frame, `list` shows the source around the current
line of that frame. Here it prints lines 275..284 of
`linux_schedule.c`, with an arrow at line 280.

These three commands — `bt`, `frame`, `list` — are 80 % of dump
debugging.

### 4.3. Inspecting the bad pointer

We want to see what `wqh` actually points at. In frame 15:

```
(kgdb) frame 15
(kgdb) print wqh
$1 = (wait_queue_head_t *) 0xfffffe00fd01a6e8
(kgdb) print *wqh
$2 = { lock = {...}, task_list = { next = 0x10217, prev = ... } }
```

**Do not trust this output uncritically.** See §3.4: `linux_schedule.c`
is `-O2`, `wqh` is `<optimized out>`, and the DWARF location for it
at this PC may be a stack slot that has since been reused. The real
faulting address comes from the trap frame (next paragraph), not
from this `print *wqh`.

To see the faulting address the CPU reported (the `%cr2` register on
x86), look at the trap frame:

```
(kgdb) frame 13
(kgdb) print *(struct trapframe *) 0xfffffe00fd01a660
```

The `tf_addr` / `tf_err` / `tf_rip` fields of that structure are the
faulting virtual address, the page-fault error code, and the
instruction pointer when the fault was taken. In this dump
`tf_addr = 1`, `tf_rbx = 1`, `tf_rip = linux_wake_up+181`, and the
instruction there is `mov (%rbx),%rbx` — the `pos = pos->next` step
of the list iteration. So the second list hop landed on `0x1`.
This is the authoritative datum; everything else is interpretation.

### 4.4. Looking at other threads

Sometimes the bug is not in the panicking thread but in another
thread that corrupted shared state. To check, on the `kgdb` prompt:

```
(kgdb) info threads             # lists every thread captured in the dump
(kgdb) thread N                  # switch to thread N
(kgdb) bt                        # backtrace of that thread
```

`crashinfo(8)` already includes one such `bt` for every CPU at the
bottom of `core.txt.0`. In our case the other CPUs were either idle
(`acpi_cpu_idle_mwait`) or doing benign work
(`linux_rcu_cleaner_func`, `taskqueue_run_locked`). Nothing pointed
to a concurrent corrupter — the bug is local to the panicking
thread's path.

### 4.5. Resolving an address inside an unsymbolicated `.ko`

If you want to find which function an address belongs to even when
the `.ko` has no debug info, `kgdb` can still tell you the symbol
because the static symbol table is present:

```
(kgdb) info symbol 0xffffffff85b98a54
wake_up_all_tlb_invalidate in section .text of /boot/modules/i915kms.ko
```

To go further (which *line* of which file), you would have to rebuild
the port with debug. Without that, we are stuck at function-name
granularity for the i915 frames — and that is what the public
`core.txt.0` shows.

## 5. The other half of the evidence: the user changed `enable_guc`

`/boot/loader.conf` on this machine ends with:

```
# Testing
#hw.i915kms.enable_guc=0
hw.i915kms.enable_guc=2
```

`hw.i915kms.enable_guc` is a **bitmask** copied from the upstream
Linux i915 driver (the port is built from Linux **6.12**, you can
prove it with `strings /boot/modules/i915kms.ko | grep drm-kmod`):

| Value | Bit 0 (GuC submission) | Bit 1 (HuC load) | Meaning                          |
|-------|------------------------|------------------|----------------------------------|
| 0     | off                    | off              | No microcontroller offload       |
| 1     | on                     | off              | GuC submission only              |
| 2     | off                    | **on**           | **HuC only** (video accel) ⚠     |
| 3     | on                     | on               | GuC + HuC (Linux default on MTL) |
| -1    | auto                   | auto             | Driver decides                   |

> **Gotcha — the FreeBSD default is not the Linux default.** The
> sysctl description on carbon reads:
> ```
> hw.i915kms.enable_guc: Enable GuC load for ... (-1=auto [default], ...)
> ```
> That string is copied verbatim from upstream Linux and is **wrong
> for this port**. The actual compiled-in default in
> `drm-latest-kmod` is `0`, set in
> `drivers/gpu/drm/i915/i915_params.h:64`:
> ```
> param(int, enable_guc, 0, 0400)
> ```
> with a comment a few lines above explaining the override:
> `enable_guc: -1 -> 0` "When the GuC is used, there is a great
> chance that the computer freezes". So:
>
> - **Linux** with no kernel arg on MTL → `-1` → auto-resolves to `3`
>   (GuC submission + HuC).
> - **FreeBSD drm-kmod** with no `loader.conf` line → `0` (everything
>   off). This is what the user originally had, and it is also why
>   the early-May dmesg shows `GUC: submission disabled` /
>   `GUC: SLPC disabled` plus the TLB-invalidation warnings (the
>   `=0` code path on MTL has its own pre-existing issue, unrelated
>   to the `=2` panic).
>
> Practical consequence: **on MTL with this port you have to ask
> for `=3` explicitly** — the upstream-tuned working value is not
> what you get by leaving the tunable unset.

The history we can reconstruct from `/var/log/messages`:

- **May 2 .. May 4 2026:** the driver loaded successfully many
  times. Logs show `GUC: submission disabled` and `GUC: SLPC
  disabled`, consistent with `enable_guc=0` (or unset).
- During those same sessions, the kernel printed
  `GT0: GUC: TLB invalidation response timed out for seqno 1`,
  multiple times. That is i915 telling us GuC TLB invalidation is
  broken on Meteor Lake in this kmod build — but the driver kept
  running.
- **Between then and 2026-06-28:** to address those TLB errors, the
  user changed `/boot/loader.conf` to set
  `hw.i915kms.enable_guc=2` (disable GuC submission, keep HuC). This
  is a reasonable workaround on paper.
- **2026-06-28 18:28:** kernel panics during `kldload i915kms` with
  the new value.

So the failure was triggered by switching from `=0` to `=2`, but `=2`
is not an *illegal* value — the upstream i915 driver supports it.
The crash is a **latent bug in the FreeBSD drm-kmod port** triggered
when the MTL GuC ends up in a state where the TLB-invalidation wake
path is reached repeatedly. The post-mortem cannot pin the precise
fault by itself, but a live experiment (next section) showed that
moving to `enable_guc=3` makes the symptom disappear entirely — which
narrows the suspect surface considerably.

### 5.1. Live experiment: does `enable_guc=3` work?

`i915kms` is not in `kld_list`, so we can change the tunable and
attempt a load without rebooting (the value is read by the module at
attach time):

```
% sudo kenv hw.i915kms.enable_guc=3
hw.i915kms.enable_guc="3"
% sudo kldload i915kms        # ~25s, returns 0
% dmesg | grep -E 'GUC|HuC|GSC|Initialized i915' | tail
drmn0: [drm] GT0: GuC firmware i915/mtl_guc_70.bin version 70.53.0
drmn0: [drm] GT0: HuC firmware i915/mtl_huc_gsc.bin version 8.5.4
drmn0: [drm] GT0: GUC: submission enabled
drmn0: [drm] GT0: GUC: SLPC enabled
drmn0: [drm] GT0: GUC: RC enabled
drmn0: [drm] Initialized i915 1.6.0 for drmn0 on minor 0
```

No GPU hangs in dmesg, no resets, no panic. The user confirmed
Xorg starts and runs against `drmn0`. The post-load `uptime` shows
the box staying up cleanly past load, which is the simplest possible
falsification of "MTL+drm-kmod is universally broken": **with full
GuC+HuC the driver is healthy on this hardware**. The hangs were
specific to the `=2` (HuC-only, GuC submission off) configuration.

The persistent fix:

```
% sudo sed -i.bak -e 's/^hw.i915kms.enable_guc=2$/hw.i915kms.enable_guc=3/' /boot/loader.conf
% grep enable_guc /boot/loader.conf
#hw.i915kms.enable_guc=0
hw.i915kms.enable_guc=3
```

## 6. Root cause: what we know, and what we don't

What is established beyond doubt from this dump:

1. **The MTL GPU was hanging in a tight loop during `i915` probe.**
   `time_uptime = 76 s`, the `kldload(2)` syscall was still in flight
   on the panicking thread, and the kernel message buffer contains
   hundreds of `GPU HANG: ecode 12:1:…` / `Resetting <engine> for CS
   error` entries on the render, blitter and compute engines, with
   periodic `GT0: Resetting chip for stopped heartbeat …` + GuC
   firmware re-load lines interleaved. i915 probe was submitting
   work, that work was hanging, the heartbeat watchdog kept
   triggering GT resets.

2. **The fatal call was `wake_up_all_tlb_invalidate → linux_wake_up`,
   on a list walk that hit address `0x1` after one iteration.**
   Faulting instruction `mov (%rbx),%rbx` with `%rbx=1`,
   `tf_addr=1`, RIP at `linux_wake_up+181`. The list walk took one
   hop before crashing.

3. **The MTL platform with this drm-kmod build was already known
   broken even at `enable_guc=0`,** because earlier successful loads
   produced `GT0: GUC: TLB invalidation response timed out` errors.

4. **The configuration matters.** A direct A/B (see §5.1) shows that
   moving to `enable_guc=3` (GuC submission **on**, HuC on — the
   upstream Linux default for MTL) lets the driver attach cleanly with
   zero GPU hangs and a working Xorg session. So the failure is
   **specific to the `=2` (HuC-only, GuC submission off) path** in
   this drm-kmod build, not to MTL+drm-kmod in general.

What we **do not** know, even now, and should not pretend to:

- The precise nature of the fault inside `wake_up_all_tlb_invalidate`
  under `=2`: use-after-free of `intel_guc_tlb_wait`, concurrent
  corruption of `wait->wq.task_list` by parallel reset paths, a torn
  pointer from an unsynchronised `xa_alloc`, or something else.
  The kgdb display of `*wqh` looks like garbage, but §3.4 shows
  that display is unreliable on a `-O2` LinuxKPI. The driver source
  (`intel_guc_submission.c:1859..1871`) shows the wait queue is
  heap-allocated and properly `init_waitqueue_head()`'d, so a simple
  "never initialised" story is ruled out.

- The mechanism by which disabling GuC submission while keeping HuC
  ends up making the TLB-invalidation wake list invalid. Plausible
  guesses (GuC-submission-off path still uses a GuC code path during
  reset; HuC alone confuses the GuC TLB bookkeeping; …) cannot be
  confirmed without a debug build of i915kms.

The honest summary is: **`enable_guc=2` puts the MTL GuC/HuC into a
broken state where every GPU batch hangs and the reset path
dereferences a stale/corrupt wait list. `enable_guc=3` (the upstream
Linux default for MTL) avoids the broken state entirely and is the
recommended value.** Pinning down the `=2`-specific bug for upstream
still needs a debug-built `i915kms.ko` — see §7.

## 7. Recovery and workarounds

| Value | Outcome on this MTL laptop                                                                 |
|-------|--------------------------------------------------------------------------------------------|
| `0` (or unset) | Driver loads, console works, but **GuC TLB invalidation timeouts** in dmesg. |
| `1`            | Untried here. GuC submission on, HuC off. May reintroduce GuC errors.            |
| `2`            | **Panics on load.** This document.                                                |
| `3`            | **Recommended.** Loads cleanly, GuC + HuC enabled, no hangs, Xorg works (§5.1). |

In order of preference:

1. **Use `enable_guc=3`.** This is the upstream Linux default on
   Meteor Lake and the value that resolves this panic on this
   hardware (proven by the §5.1 experiment). Persisted by:
   ```
   sudo sed -i.bak -e 's/^hw.i915kms.enable_guc=2$/hw.i915kms.enable_guc=3/' /boot/loader.conf
   ```
   To **test** a different value without rebooting (works because
   `i915kms` is not in `kld_list` — it is loaded on demand after
   single-user is already up):
   ```
   sudo kldunload i915kms 2>/dev/null   # if already loaded
   sudo kenv hw.i915kms.enable_guc=3    # set the tunable
   sudo kldload i915kms                 # ~25s on first attach
   dmesg | tail -50                     # confirm GUC/HuC init
   ```
   The `kenv` route avoids editing `/boot/loader.conf` until you are
   sure of the value.

2. **Emergency fallback if `=3` ever stops working** (e.g. after a
   future port update): boot with `=0` for a working console with no
   GPU accel. From the loader prompt (`OK`):
   ```
   set hw.i915kms.enable_guc=0
   boot
   ```
   Fix `/boot/loader.conf` from multi-user afterwards. **Do not** use
   `=2` on this hardware — that is the panic path documented here.

3. **If you do not need GPU acceleration at all,** keep `i915kms`
   out of `kld_list` (already the case in `/etc/rc.conf` here:
   `kld_list="filemon cuse"`). `efifb` is enough for a console.

4. **Improve the next dump** (still useful if you want to upstream a
   fix for the `=2` path).

   - Boot a `GENERIC` (not `-NODEBUG`) kernel. INVARIANTS + WITNESS
     are likely to catch the uninitialised list earlier and panic
     with a more useful message than `page fault`.
   - Rebuild the drm-kmod port with debug info so the i915 frames
     in `kgdb` get file/line numbers. The port tree is on `bigone`,
     not on `carbon`; build there and ship the result:
     ```
     # on bigone (where /usr/ports/ is populated):
     cd /usr/ports/graphics/drm-latest-kmod
     sudo make WITH_DEBUG=yes package
     # then scp the resulting .pkg to carbon and `pkg add` it
     ```
     `.debug` files land under `/usr/lib/debug/boot/modules/` on
     carbon after install. The next dump will resolve
     `wake_up_all_tlb_invalidate`, `intel_uc_suspend`, etc. to
     source lines.
   - Before reloading after any config change:
     ```
     sudo sysctl debug.bootverbose=1
     sudo dmesg -c                  # clear ring buffer
     sudo kldload i915kms
     dmesg | grep -E 'i915|drm|GuC|HuC' | tee i915-load.log
     ```

5. **Upstream report.** With a debug-built kmod and the easy
   reproducer (`kldload i915kms` with `hw.i915kms.enable_guc=2` on
   MTL), file at <https://github.com/freebsd/drm-kmod/issues>.
   Include:

   - kernel: `uname -a`
   - GPU: `pciconf -lv vgapci0`
   - port: `pkg info drm-latest-kmod`
   - panic + backtrace: `/var/crash/core.txt.last`
   - the trigger value of `hw.i915kms.enable_guc` (=2 panics, =3
     works — the A/B is the strongest signal for the maintainer)
   - and mention the **pre-existing** TLB-invalidation warning under
     `enable_guc=0` — it is plausibly the same underlying GuC/MTL
     issue and useful context for whoever triages this.
