Gotchas learned this time:
- Guest dumps go to the host share, not /var/crash: savecore_enable=NO, /etc/rc.local saves to
  /mnt/host/crash/frrtopo once the late 9p mount is up. A crash can damage the guest root (one
  panic was followed by a UFS panic that lost the saved vmcore); fsck it offline from the host
  after several panics: mdconfig -a -t vnode -f /zroot/vm/frr-topotest.img, fsck_ffs -fy
  /dev/gpt/frrvm-root until fsck_ffs -fn is clean, mdconfig -d.
- A file written in the guest just before a panic may be lost (no sync on panic): a repro binary
  came back 0 bytes and a "survived" run was void. sync after building anything you will crash.
- kgdb in the guest: commands on stdin (no -batch/-x), no curthread symbol
  (use cpuid_to_pcpu[N]->pc_curthread), symbols at /mnt/host/kernel.debug (stock) or
  /mnt/host/kernel-rtfix/kernel.debug (patched).
- Each panic leaves two "panic:" lines in the console log (panic + savecore). clear_tmp_enable=NO
  keeps /tmp/topotests, so the test behind a crash can be found; FreeBSD pids get reused fast.
- Never run a hammer or the reproducer on the workstation.
